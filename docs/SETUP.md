# Budgetwise production deployment

This guide targets **Cloudflare Workers + the Cloudflare Vite plugin + D1**. Do not use a static-only Pages deployment: the application needs a Worker for authenticated API routes and persistent D1 access.

## Repository and build settings

- Git repository: https://github.com/HdeSy/WTF_MyCode
- Worker name: `budgetwise-personal-tracker`
- Root directory: repository root (`/`)
- Cloudflare Workers Builds build command: `npm install --no-audit --no-fund && npm test && npm run typecheck`
- Deploy command: `npm run deploy` (runs D1-ID validation, then `npm run build` and `wrangler deploy`)
- Frontend output: generated by the Cloudflare Vite plugin; the generated Wrangler config points to the client asset output. Do not manually set a Pages `dist` output directory.
- Runtime entry: `worker/index.ts`
- Persistent database binding: `DB` → D1 database `budgetwise-db`
- Static assets binding: `ASSETS`
- Compatibility flag: `nodejs_compat`
- Logs: Workers observability enabled; invocation URL logging disabled to avoid collecting unnecessary request metadata.

## Required Cloudflare account actions

The ChatGPT GitHub connection can edit this repository, but it does not have a Cloudflare account/API connection. No Cloudflare resource, secret, domain, or deployment can be created from this repository connection alone. Complete these steps in the Cloudflare dashboard:

1. Open **Workers & Pages** and connect GitHub if it is not already connected. Select `HdeSy/WTF_MyCode`, production branch `main`, root directory `/`, and Worker name `budgetwise-personal-tracker`. Enable automatic production deploys from `main`; keep feature-branch preview deployments separate from production.
2. In **D1**, create a **new, empty** database named `budgetwise-db` in the same account. Copy its database ID into `wrangler.jsonc` in the repository and commit that non-secret configuration change. Do not use a database ID from another account.
3. In the Worker settings, add `BETTER_AUTH_SECRET` as an encrypted **Secret**, using a unique random value of at least 32 bytes. Never store it in source control, a committed `.dev.vars`, or logs. The Worker will return HTTP 503 for auth/private APIs until this secret is configured.
4. Once the first Worker URL is known, set `BETTER_AUTH_URL` as a normal Worker variable to the exact origin (for example, `https://budgetwise-personal-tracker.<your-workers-subdomain>.workers.dev`). Do not include a trailing path. If you later switch to a custom domain, update this variable to the final HTTPS origin and redeploy.
5. Ensure the deployed Worker is configured to use the same `DB` binding and D1 database ID from `wrangler.jsonc`. Keep production and preview databases separate.
6. Set the Git integration's build command to the one above and deploy command to `npm run deploy`. The deploy lifecycle validates that the D1 ID is configured, builds the app, and runs `wrangler deploy`; the Cloudflare Vite plugin generates the deployment asset configuration during the build.

## Database migration safety

The repository has migrations `0000_auth_tables.sql` through `0003_budget_categories_goals.sql`. Migration `0002_transaction_enhancements.sql` rebuilds the transactions table, copying existing rows to the new schema. Automated migration tests verify the copy and new schema, but **do not assume the live database is empty or apply these files to an unknown existing database**.

For a brand-new database, first confirm the database name and ID in the dashboard, then from a trusted terminal with Wrangler authenticated to the intended Cloudflare account:

```sh
npm test
npm run typecheck
npm run build
npm run validate:deploy
npx wrangler d1 migrations list budgetwise-db --remote
npx wrangler d1 migrations apply budgetwise-db --remote
npx wrangler d1 migrations list budgetwise-db --remote
```

Inspect the database ID in `wrangler.jsonc` before each command. Wrangler's D1 migration apply captures a backup, but still verify the target database. If the database already contains records or has any migrations applied, stop and inspect the migration history and create/verify a restorable backup before proceeding. Never drop or recreate a production database to resolve a migration mismatch.

## Authentication and launch gate

Before using real financial records, test registration, sign-in, sign-out, expired sessions, incorrect passwords, rate limiting, and isolation between two separate users. Verify that a user cannot view, update, export, or delete another user's transactions, accounts, categories, budgets, or goals. Confirm the Better Auth table schema against the installed version. Email verification and password-reset delivery are not configured by this repository yet; decide and implement a secure recovery flow before treating the app as a public financial service.

## Live smoke tests after deployment

1. Open `https://<your-workers-subdomain>.workers.dev/api/health`; expect a minimal JSON health response.
2. Open the home page and verify HTTPS and static assets load without console errors.
3. Register a test account, sign in, create a test account/category/transaction, edit it, then delete it. Use only disposable test data.
4. Verify daily, weekly (Monday–Sunday), monthly, and custom date range totals around Asia/Manila midnight and a Monday boundary.
5. Create a savings goal and contribution, then verify goal progress and budget calculations.
6. Download daily, weekly, monthly, and custom-range Excel reports. Open each in Microsoft Excel 2016 or newer and check all four worksheets, filters, formulas, dates, pesos, and totals.
7. Repeat the access-control tests with a second account. Delete test data after verification.

## Custom domain and HTTPS

After the Worker works on its `workers.dev` address, open **Workers & Pages → budgetwise-personal-tracker → Settings → Domains & Routes → Add → Custom Domain**. Use a domain or subdomain that you control and that is active in the Cloudflare account. Cloudflare creates the required DNS record and provisions the TLS certificate for a supported Custom Domain. Do not manually replace existing production DNS records without checking what they serve. Set `BETTER_AUTH_URL` to the exact custom HTTPS origin and redeploy, then test registration/login cookies and the Excel download on that origin.

No domain has been selected or connected yet, so the final URL is not known.

## Deploying future updates

With Cloudflare Workers Builds connected to GitHub, pushing or merging commits to `main` triggers a production build and deployment. Review the GitHub/Cloudflare build status after every deployment. Database schema changes must be reviewed and applied as an explicit migration step before code that depends on the new schema is released. Keep migrations additive when possible; back up and test any migration that rebuilds or drops a table.

## Costs and operations

Workers and D1 have free and paid usage plans; actual charges depend on request, CPU, storage, and database usage. A custom domain requires owning the domain; Cloudflare DNS and TLS setup for a supported Worker Custom Domain do not require buying a separate TLS certificate. Review current Cloudflare pricing and your account's usage limits before enabling production traffic. Email delivery for verification/password reset, if added, may require a separate provider and could have additional costs.
